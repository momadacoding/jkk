# 重放时快照内容按基线走（事故分析 6.10）

日期：2026-11-06。来源：2026-11-05 SVN 跟进事故分析第 6.10 节（用户在对话中提供，未入库）。实现日志：`docs/superpowers/plans/2026-11-06-svn-snapshot-replay-decisions.md`。

## 1. 问题

「`svn up` 之后把整个工作区提交进 git」的快照提交，把别人的 SVN 改动记成了自己的 commit。分支停在旧基线上时，跟进要把它重放到新基线，SVN 之后又改了同一片代码，于是：

- **冲突**：2026-11-05 第二次跟进 37 个冲突，其中 35 个文件在快照里的版本与当时的 r66050 基线逐字节相同，是纯 SVN 内容。
- **静默合错**：`MetaLeagueDbsApp.cpp` 合出两份同名函数；`sim_lowmem.lua`（SVN 已改名）被加回分支。

现有的 F2 ①（「自己提交的路径取 SVN 版本」，分析 §6.5）按作者和失焦快照判断，覆盖不到「快照里是同事改动」的情形。

## 2. 规则

重放 commit C 时，对 C 改过的每个路径 p（`diff-tree -r C^ C`，含删除）：

> 1. C 里 p 的条目（mode + blob，删除记作「不存在」）等于某个**比这条分支自己的基线更新**的基线提交里 p 的条目，且不等于分支自己的基线里 p 的条目；
> 2. C^ 里 p 的条目也是纯 SVN 的：等于分支自己基线里的，或者也出现在某个更新的基线里。
>
> 两条都满足，就把 p 放进 F2 ① 已有的「换成 SVN 版本」集合 P。

第 2 条是独立 review 补的：换的手段是把 p 写回 C^ 的条目。C^ 里要是有我自己的内容（前面的 commit 改过 p，后来在 SVN 侧撤掉、update 后整包提交），写回去就把撤掉的改动复活了，而报告还说「采用了新基线的版本」。这种情形不命中，退回原来的重放。

放进 P 的路径在 C' 里换回 C^ 的条目，merge-tree 看到「theirs 没改」，直接取新基线的版本（与 F2 ① 同一套机制，`svn_replay.rs` 不改）。

- 「更新的基线」= `scope..NEW` 上的基线提交，`scope` 是这条分支自己的基线（merge-base）。只比 git 对象，不联网。
- 排除「等于分支自己基线」的条目：用户故意把文件退回到更老版本时不受影响。
- Local-Only commit 不适用：它的内容等于基线时说明补丁被带上了服务器，那是 F3 泄漏检查要报的，不能静默收掉（与 F2 ① 同一个理由）。
- 判定出错（读不了某个基线等）时这条 commit 的 P 不加东西，退回原来的行为。

边界（接受）：

- 用户有意把文件停在某个比分支基线新、但比 NEW 旧的 SVN 版本时，会被换成 NEW 的版本。跟进报告单独列出这样处理过的文件；手动跟进在冲突框里**动手之前**列出。commit 里的内容本来就等于 NEW 的不列：换不换都一样。
- 只认「有基线 commit 的那个版本」。svn up 到 r100 整包提交、中途没点过跟进、到 r200 才跟进时，`scope..NEW` 里没有 r100 的条目，规则不命中，仍会冲突。2026-11-05 能命中，是因为前一次跟进恰好发布了 r66050 的基线。要覆盖这种情形就得联网取 r100 的内容，与离线判定的原则冲突，不做。

## 3. 用在哪

| 入口 | 做法 |
|---|---|
| 对象层跟进，当前分支 | `superseded` = F2 ① ∪ 本规则（按当前分支的 scope） |
| 对象层跟进，其他分支 | 同上，按各自的基线算 |
| 手动跟进（会写磁盘的 rebase） | commit 里有命中路径时，先在对象层为每个 commit 造一个 C'（树换掉命中路径、挂在原 C^ 上、带原作者与 message），rebase 用 `-i` 加一份写好的 todo 逐个 pick C'。没有命中时与原来完全相同 |

手动跟进不改成别的重放方式：继续、放弃、冲突出口都按 `git rebase` 的现有状态机走，只换 todo 里的 commit。todo 由 `GIT_SEQUENCE_EDITOR` 写入，内容放环境变量，不经命令行引号（仓库路径可能含空格、中文）。`rebase.missingCommitsCheck`、`rebase.autoSquash` 用 `-c` 钉住，不受用户配置影响。

细节：

- 整个 commit 都是快照内容（C' 与 C^ 同树）时不放进 todo：rebase 会保留「一开始就为空」的 commit，`--empty=drop` 只丢重放后才变空的。一个都不剩时 todo 是 `noop`，分支直接落到新基线上，与对象层把它记成 dropped 一致。
- todo 超过 Windows 单个环境变量的上限（约 30K 字符，约 650 个 commit）时退回原样 rebase，记日志。
- C' 没有 ref 指着。rebase 开始之前用 `cat-file --batch-check` 核对它们还在：记录搁置太久碰上 gc 时，报错并提示「放弃」后重新跟进，这时分支还没动。

## 4. 顺带修：对象层跟进合错也报「完成」（PR 119 遗留）

对象层跟进只移 HEAD、不写磁盘。重放干净却合错时（W14），HEAD 落在错误的 tip 上，「本地改动」出现反向修改，界面照样报完成。

判据：重放后当前分支 tip 与 NEW 不同、且在 `scope..NEW` 改过的路径里，磁盘内容等于 NEW 的版本（SVN 没有本地修改，磁盘 = BASE = NEW）而 tip 的 blob 不同的，或者 tip 有、NEW 与磁盘都没有的（被带回的文件），列入报告的 `drift`，报告标成需要留意。只差 mode 的不报。跟进照常完成：按分析 §6.12 的设计，手动点「跟进」时这种情形可以完成，只是不能静默。核对本身出错只记日志，不让跟进失败。

它分不清「合错」与「我在磁盘上撤了某个 commit 的改动、还没提交这次撤销」，所以文案只说「对不上，请核对」，不断言是合错。

## 5. 测试（`src-tauri/tests/svn_follow.rs`，临时 fixture）

- 快照提交、分支停在旧基线、SVN 之后又改了同一行：跟进不冲突，取新基线版本，报告列出
- 快照里有被 SVN 删除的文件：跟进后分支里没有它
- 快照混着真冲突：冲突只剩真冲突那个文件；手动跟进的 rebase 冲突也只剩它
- Local-Only commit 的内容等于新基线：不按本规则换
- 退回到分支自己基线版本的改动：不按本规则换
- 对象层跟进合错（merge driver 模拟）：报告列出 drift
