# 体检基线：从常驻入口改成按症状提示

日期：2026-11-25　状态：B + C 实现中（用户 2026-11-25 放行）　版本：jkk 0.10.2 起

相关：`src/engine/svnSync.ts`、`src/components/BaselineBanner.tsx`、`src-tauri/src/engine/svn_init.rs::check_current_baseline`

**一句话：** 常驻横幅让用户「怀疑时去体检」，可正常使用时用户没有理由怀疑，也不知道什么时候该怀疑。改成 jkk 自己发现症状、主动提示（B），并把常驻横幅挪走（C）。

## 1. 现象

基线和工作副本对得上时，仓库页顶部一直挂着一行：

```text
revision 对得上不代表基线记的内容是对的——体检会拿基线跟服务器逐个文件比一遍。  [体检基线] [TortoiseSVN 钩子…]
```

- 用户第一反应：「这是干啥？我需要做什么吗？」它读起来像告警，其实只是一个常驻入口。
- 改成「一切正常。怀疑 jkk 记错了 SVN 内容时，可以点『体检基线』」之后，用户指出：用户怎么知道该怀疑？正常使用就不应该怀疑。问题不在措辞，而在把「判断何时该体检」交给了用户。

## 2. 现状（2026-11-25 读代码确认）

| 位置 | 事实 |
|---|---|
| `src/engine/svnSync.ts` `needsStandaloneCheck` | 没有失同步横幅、没有行尾迁移、基线没丢时就显示这一行，正常状态下一直在 |
| `src/components/BaselineBanner.tsx`（`standalone &&` 那段） | 渲染这一行和两个按钮 |
| `src/components/RepoTab.tsx` `handleCheckBaseline` | 调 `check_current_baseline`。这是发现「基线记的内容与服务器不符」（`Lying`）的唯一入口；发现后就地提供「重建基线」 |
| `svn_init.rs` `check_current_baseline` | 工作副本有改动时也能用；SVN 认为改过的那些文件，体检证明不了什么 |
| `svn_server_set.rs`、`svnSync.ts` `SVN_AUDIT_*` | 自动的后台服务器核对（`svn ls -R` 清单与磁盘比，抓漏收）。只在发现问题时出横幅，不查内容，不能替代体检 |

先例：后台服务器核对做成自动的理由写在 `svnSync.ts` `SVN_AUDIT_POLL_MS` 的注释里——不知道出了事的人不会去点一颗写着「检查一下有没有出事」的按钮（2026-09-19 用户原话：它不是工作流的一部分）。常驻体检入口是同一个问题。

## 3. 基线什么时候会在 revision 对得上时记错

代码注释（`svn_init.rs` 体检文档、`svnSync.ts`）里列了五种，核对后只有三种属于这一类：

| 情形 | 归属 |
|---|---|
| 有人在项目根跑了递归 update，把 external 退回旧版本 | **不属于**：revision 变了，现有的 `pinnedReset` / `diverged` 横幅已经抓到 |
| 跟进或同步中途崩溃，恢复没走完 | 属于 |
| 旧版 jkk 录基线时录错了 | 属于 |
| 有人手工往 `svn/base` 上提交过 | 属于 |
| `svn revert` 这类不改 revision 的外部操作 | **不属于**：只改磁盘、不会让基线变错（`svn_sync.rs` 模块头「这条检查抓不到 svn revert」），由 git 状态那一侧看见 |

用户能看到的症状：jkk 的「本地改动」里出现自己没改过的文件，而 TortoiseSVN 显示这个文件没有修改。git 和 SVN 两边的状态 jkk 本来就都在读，这个症状它自己就能发现。

## 4. 目标与非目标

目标：

- 正常使用时界面上不出现体检相关的东西
- 基线真出问题时，jkk 主动提示，第一句说清要你做什么
- 手动体检的入口保留，只是不常驻

非目标：

- 不改体检本身的判据（`check_current_baseline`）
- 不改后台服务器核对
- 本期不做后台自动体检（方案 A）
- 本期不做反方向的症状（见 §6.5）

## 5. 方案对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **B 按症状提示**（采用） | 发现「git 说改了、SVN 说没改、分支提交没碰过」的文件时出横幅，按钮是「体检」 | 不联网；提示正好出现在用户会困惑的时候 | 只覆盖磁盘上没被改过的文件 |
| **C 挪走常驻入口**（采用） | 去掉常驻横幅；「体检基线」「TortoiseSVN 钩子…」挪进工具栏的「SVN ▾」菜单 | 正常时界面上什么都没有 | 单做 C，仍要用户自己想起来去点 |
| A 后台自动体检 | 并进后台服务器核对的节奏，发现问题才出横幅 | 看不见的错也能抓到 | 多一次联网；2026-11-25 日志里后台核对跑了 45.7 s，与跟进同时在跑 |

A 等 B 上线后，看还有没有漏掉的情形再决定。

## 6. B 的设计

### 6.1 判定条件

文件 `p` 同时满足下面四条，算「jkk 与 TortoiseSVN 看法不一致」：

1. **前提**：失同步判定是 `InSync`、当前分支不落后基线、行尾迁移已完成、基线分支在、没有未收尾的同步——也就是原来常驻入口会出现的那些时刻（`needsStandaloneCheck` 的条件 + 横幅没被压住）。
2. git 说 `p` 有改动：磁盘 ≠ HEAD（`git diff --name-only --diff-filter=M HEAD`）。
3. 分支上的提交没碰过 `p`：HEAD 里的 `p` 等于 `svn/base` 里的 `p`（`git diff-tree <svn/base> HEAD` 里没有它）。
4. SVN 说 `p` **完全干净**：此刻现跑的 `svn status -v --xml -- <p>` 里，`item="normal"`、`props="none"`、不是 `copied`。

#### 为什么要第 1 条

`externallyAdvanced`（TortoiseSVN 已经 update、jkk 还没跟进）时，SVN 刚更新下来的文件同样满足 2–4：磁盘是新内容，SVN 说干净，分支没碰过。那时顶部已经有「SVN 侧有新内容 → 跟进」横幅，再报「基线记错了」是自相矛盾。部分跟进留下的文件（heldBack）同理。分支落后基线时，「本地改动」是相对旧基线算的，也会多出这类文件，那时有「当前分支落后基线 → 跟进」横幅。

#### 为什么要第 3 条

用户在 TortoiseSVN 里 revert 掉自己的 Local-Only 补丁时，这个文件同样是「git 说改了、SVN 说没改」。那是有意为之，jkk 已有「放回补丁」提示，不能报成基线错了。

因为第 1 条保证了当前分支包含 `svn/base`，`svn/base..HEAD` 恰好就是分支自己的提交，直接比两棵树即可。

#### 为什么第 4 条必须**现跑**，不能复用失同步检测那遍扫描

失同步检测只在 wc.db 戳变化时重跑（`svn_sync.rs` `read_root_revs` 文档：第一档看 wc.db 戳）。但 `svn status` 的「modified」是查询那一刻拿磁盘和 pristine 比出来的，用户改文件不写 wc.db。复用缓存的话，用户刚改、还没提交的文件会同时满足 2、3 和（过时的）4，每一处新改动都会被报成「jkk 记错了」。

所以每次判定只对候选文件（满足 2、3 的 W-file）现跑一次本地 `svn status`。不联网，候选通常就是用户正在改的那几个文件。

#### 为什么第 4 条写成「完全干净」而不是「不是 modified」

只在 git 里新增的文件是 `unversioned`，丢了的是 `missing`，还有 `conflicted`、external 根、只改了属性的 `props="modified"`、复制来的 `copied`。这些都不是「SVN 认为它等于服务器」，不能算进来。

### 6.2 横幅

```text
点「体检」核对 3 个文件：jkk 记的 SVN 内容可能不对
TortoiseSVN 显示这些文件没有修改，你的分支提交也没碰过它们，但 jkk 的「本地改动」里有。
体检会拿基线和 SVN 服务器逐个核对；确认基线记错了，可以就地重建基线。
  · LuaScripts/xxx.lua
  · ...
                                                   [体检]
```

- 第一句是动作（目标第 2 条）。
- 「体检」沿用 `handleCheckBaseline`：发现基线记错（`Lying`）时就地提供「重建基线」。重建只移动 `svn/base`、不推进工作分支，于是之后分支落后基线，前提第 1 条不再成立，这条横幅让位给「当前分支落后基线 → 跟进」；跟进之后 HEAD 与磁盘一致，文件从「本地改动」里消失。
- 体检报告基线没问题（`Verified`）时，同一组文件不再提示，直到文件清单变化。否则行尾 / 关键字展开这类体检查不出差异的情形（§9 第 3 条）会让横幅一直挂着。断网（`NotChecked`）不算，横幅留着。
- 最多列 50 个文件，候选最多现查 1000 个（见决策日志）。

### 6.3 什么时候算

跟着「本地改动」刷新（`state.status` 变化）算，与「缺 Local-Only 补丁」横幅同一个节奏。前提不成立、或「本地改动」为空时前端不调后端；候选为空时后端不起 svn 进程。

### 6.4 覆盖不到的

- git 的 stat cache（spec §7.3.0）可能让某个文件暂时不显示为已修改，B 跟着漏判，直到它的 mtime 被碰一下。
- 磁盘上被用户改过的文件（SVN 显示 modified）：体检本来也证明不了它们。

### 6.5 反方向的症状（本期不做）

SVN 说改了、git 说干净、分支没碰过，意思是磁盘等于基线、但不等于 pristine，基线同样是错的；表现是 TortoiseSVN 里冒出你没改过的文件，jkk 什么都不显示。要发现它，得对整个白名单跑一遍 `svn status`（公司机器上秒级），不能挂在每次刷新上。可以考虑并进失同步检测（它本来就跑这遍扫描），留到 B 上线后再定。

## 7. C 的设计

- 删掉常驻横幅（`needsStandaloneCheck` 那一行）。
- 工具栏「更新」「交付」后面加一个「SVN ▾」按钮，菜单里是「体检基线」「TortoiseSVN 钩子…」。
- 「体检基线」在这些时候置灰并说明原因（与原来常驻入口隐藏的时机一致）：同步进行中或未收尾、基线分支不见了、行尾迁移没做、SVN 侧有新内容还没跟进（那时体检用的是旧基线，必然把新内容报成不符，而跟进本身就包含体检）。
- 失同步横幅上本来就有的体检按钮不变；钩子失效横幅的「重新注册」不变。
