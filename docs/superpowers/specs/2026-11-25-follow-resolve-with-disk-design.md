# 跟进冲突：用磁盘上的内容跟进

日期：2026-11-25　状态：方案已选定，实现中　发现版本：jkk 0.10.2

一句话：同一个冲突已经在 TortoiseSVN 里解决过时，磁盘上的文件就是想要的结果。jkk 在冲突框里给一个「用磁盘上的内容跟进」按钮，用户点一下就把分支跟上去，不再解第二遍，也不写工作区。冲突框不再内嵌冲突标记，改成用外部工具（Beyond Compare）对比的按钮。

实现计划：`docs/superpowers/plans/2026-11-25-follow-resolve-with-disk.md`。

## 1. 背景与问题

### 1.1 现场

- Client 仓库，基线停在 r70684。在 TortoiseSVN 里 update 后，SVN 侧有 399 个文件有新内容。
- `LuaScripts/Client/SettingMgr.lua`：SVN 上 r70760（同事）改过，我的提交 `7cc9113265` 也改了同一处。update 时 SVN 报冲突，我在 TortoiseSVN 里解决并标记了 Resolved。
- jkk 自动跟进时，把这个提交重放到新基线上又冲突了，横幅显示「没有自动跟进：当前分支的提交重放到新基线上，有 1 个文件冲突」。

### 1.2 现在的流程哪里不好

1. 冲突要解两遍：SVN 里一遍，jkk 的手动跟进里再解一遍，内容完全相同。
2. 手动跟进会改写工作区：先 stash、再 rebase、最后放回。那 399 个 SVN 文件在 git 看来也是未提交改动，会被改写两遍，Unity 开着时可能触发重新导入。
3. 冲突框里的预览看不懂：内嵌的是 git 冲突标记（`<<<<<<< 新基线（SVN）` / `=======` / `>>>>>>> 你的提交`），不知道上下两半各是什么。

### 1.3 为什么现在不复用（已读代码确认）

| 位置 | 事实 |
|---|---|
| `src-tauri/src/engine/svn_follow.rs` `prepare` 里的 `replay_branch` 调用 | 跟进判冲突只看 git 对象（merge-tree 重放），不看磁盘。 |
| `svn_follow.rs` `auto_blocker` 的「方案 B」 | 磁盘只在不冲突时拿来对照：重放结果与磁盘逐字节相同就放行。 |
| `src-tauri/src/engine/svn_sync_stash.rs` `settle_untouched_conflicts` | 手动跟进放回改动时的冲突按跟进前的磁盘解决；rebase 冲突这一步没有同样的处理。 |
| `src/engine/svnFollow.ts` `previewSection` | 冲突框的预览直接贴第一处冲突块的文本。 |

关键观察：「本地改动」= 磁盘 − 分支。分支里这个文件等于磁盘时，「本地改动」就是干净的。磁盘上 SVN 合并好的内容正好就是重放冲突该有的答案。

## 2. 目标与非目标

目标：

- 已在 SVN 里解决过的冲突，点一次就能跟进完成
- 跟进过程不写工作区
- 点之前能用熟悉的外部工具看清会写进提交的内容

非目标：

- 不做全自动：自动跟进仍然不碰冲突
- 不改手动跟进的流程
- 第一版不处理多个提交改过同一文件的情形

## 3. 方案对比与决定

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A（选定） | 冲突框加「用磁盘上的内容跟进」按钮；重放时把冲突文件的结果直接换成磁盘内容，然后照常发布 | 点一次；不 stash、不 rebase、不写工作区 | 重放流程要加「指定结果」的口子，新代码最多 |
| B | 手动跟进停在 rebase 冲突时，把冲突文件换成跟进前的磁盘内容（从 stash 取） | 沿用现有继续 / 放弃状态机，改动小 | 仍要 stash + rebase，399 个文件改写两遍 |
| C（否决） | 自动跟进直接按磁盘内容解决，不问 | 零点击 | 分不清「SVN 合并结果」和「合并后又手改的未提交内容」，后者会被静默写进提交；违反「冲突要人判断」（条件 7） |

选 A：唯一同时做到「只解一遍」和「不写工作区」的方案；风险点（把不该进提交的内容带进去）由前置检查和点击前的对比兜住。

## 4. 操作流程

1. 点横幅上的「跟进」。jkk 发布新基线（现在就是这样），检查冲突文件能不能直接用磁盘内容（第 6 节），能的话带着替换把整条分支试重放一遍，确认后面没有别的冲突。这一步只建 git 对象，不写磁盘。
2. 看冲突框。能用磁盘内容时，文件那一行显示 ✓ 和对比按钮；不能时显示 ✗ 和原因，只剩「手动跟进」。
3. 点对比按钮，在 Beyond Compare 里看：右边（磁盘）比左边（SVN 新版本）多出来的，是不是都是自己的改动。这些就是跟进后提交里这个文件的改动。右边是磁盘上的真实文件，在工具里改了也算数。
4. 点「用磁盘上的内容跟进」。jkk 按最新的磁盘内容重新检查，通过后把分支移到新基线上、拼回暂存区，不写工作区的任何文件。
5. 看结果：跟进报告多一节「按磁盘内容解决的冲突」；横幅消失；「本地改动」里不再有那 399 个文件和这个冲突文件；分支图上提交挂在新基线上。

| | 现在（手动跟进） | 方案 A |
|---|---|---|
| 操作 | 跟进 → 手动跟进 → 改文件 → 暂存 → 继续 | 跟进 → 对比 → 用磁盘上的内容跟进 |
| 冲突解几遍 | 2 遍（SVN、jkk 各一遍） | 1 遍（SVN 里那遍） |
| 写工作区 | 收起、rebase、放回，399 个文件改写两遍 | 不写 |

## 5. 冲突框设计

### 5.1 能用磁盘内容时

```text
跟进遇到冲突
把提交 7cc9113265 重放到新基线上时，有 1 个文件冲突：

  LuaScripts/Client/SettingMgr.lua
  SVN 上 r70760 同事改过，你的提交也改了同一处。
  ✓ 你已经在 SVN 里合并好了，磁盘上就是合并结果。
  [用 Beyond Compare 对比]  左：SVN 新版本 r70760　右：磁盘上的合并结果

点「用磁盘上的内容跟进」：你的提交里这个文件会变成磁盘上的样子，不写工作区。
                         [Cancel]  [手动跟进]  [用磁盘上的内容跟进]
```

### 5.2 不能用磁盘内容时

```text
  LuaScripts/Client/SettingMgr.lua
  SVN 上 r70760 同事改过，你的提交也改了同一处。
  ✗ 不能直接用磁盘上的内容：磁盘上还有冲突标记
  [用 Beyond Compare 对比]  左：SVN 新版本 r70760　右：你的提交
                                       [Cancel]  [手动跟进]
```

### 5.3 规则

- 不再内嵌冲突标记预览，改成外部对比按钮。按钮文字用配置里的工具名（默认 Beyond Compare）。
- 「会写工作区」的红色警告只在只剩手动跟进时出现。能用磁盘内容时点「手动跟进」，另弹现有的手动跟进确认框（带警告）。
- 没配对比工具时才退回文本预览，并加一句话说明上下两半各是什么。

## 6. 前置检查

任一条不满足就不显示按钮，退回现在的流程（只有「手动跟进」），并在框里写明原因。

| 检查 | 防什么 | 不满足时写的原因 |
|---|---|---|
| SVN 状态不是冲突 | SVN 里还没真正解决 | 跟进的预检（`check_recordable`）已经拒绝白名单内的任何 SVN 冲突，走不到冲突框，这里不再重复 |
| 是文本内容冲突：merge-tree 给了 stage 1/2/3，都是普通文件，内容不含 NUL | 修改对删除、二进制、改名、mode 冲突时下面几条比不出意义 | 不是文本内容冲突（修改与删除撞上 / 二进制文件 / …） |
| 磁盘上有这个普通文件 | — | 磁盘上没有这个文件 |
| 磁盘上没有 `<<<<<<<` / `>>>>>>>` 冲突标记 | TortoiseSVN 允许带着标记点 Resolved | 磁盘上还有冲突标记 |
| 分支上（基线之后）只有一个提交改过这个文件 | 磁盘内容只有一份，分不出该归到哪个提交 | 有 N 个提交改过它 |
| 磁盘内容 ≠ 分支旧内容 | 那是已有的「磁盘是旧内容」情形，SVN 那边的改动不在磁盘上 | 磁盘上还是你提交里的版本 |
| 磁盘内容 ≠ 新基线 | 等于在 SVN 里放弃了自己的改动（第 10 节问题 1） | 磁盘上就是 SVN 的新版本 |
| 冲突块以外的部分，磁盘与 git 自己合出来的结果逐行一致 | 合并之后又在别处手改、还没提交的内容被带进提交 | 冲突处以外还有别的改动 |

## 7. 失败、安全与边界

- 点击时重新核对磁盘：弹框之后磁盘变了（包括在 Beyond Compare 里改过），按最新内容重跑全部检查，通过才继续；不通过就回到冲突框（按最新结果重画），什么都不动。
- 危险方向是把不该进提交的内容带进去。防线：第 6 节的检查、点击前的对比、跟进报告单列这些文件。冲突块内部若混着未提交改动无法区分，由对比这一步交给人看。
- 检查假阴性可以接受：git 与 SVN 的合并算法划的冲突块可能不同，导致检查不通过。方向是安全的，只是退回手动跟进。
- 不写工作区：与现有对象层跟进相同，只动 ref 和索引；崩溃恢复沿用现有 journal 流程。
- 回滚：回退代码即可。跟进报告新增字段加 `#[serde(default)]`，旧 journal 照常读出。

## 8. 实现要点

1. 重放：`svn_replay::replay_onto` 支持「这个提交的这个文件，冲突时结果直接用指定 blob」。不能只把提交里的文件换成磁盘内容：合并基准仍是旧内容，冲突处照样冲突，要在合并结果上覆盖。
2. 准备阶段：冲突时为每个冲突文件算「能不能用磁盘内容」及原因，放进 `ConflictDetail`；全部能用的话带着替换继续试重放。磁盘内容按 `git add` 的过滤规则算 blob。
3. 新命令：`svn_follow_with_disk(path, files, base)`，`files` 是冲突框里列出的文件，`base` 是冲突框对比用的新基线（不一致时回到冲突框）。属于 Tauri 命令签名变更，要在 `pnpm tauri dev` 的真实窗口里验证。
4. 外部对比：`external_diff.rs` 的 `DiffTarget` 新增「提交 vs 工作区文件」（`Worktree`）。「SVN 新版本 vs 你的提交」用现成的 `Range`。
5. 前端：冲突框改成独立弹框 `FollowConflictDialog`，文案在 `src/engine/svnFollow.ts`，去掉内嵌预览。

| 问题 | 决定 | 理由 |
|---|---|---|
| 1. 磁盘内容 = 新基线（在 SVN 里选了「用他们的」） | 第一版不显示按钮，写原因 | 替换后提交对这个文件的改动消失；提交只改了这个文件时 `drop_empty` 会把整个提交丢掉，需要另写文案与测试。少见，手动跟进兜得住 |

## 11. review 补充（2026-11-25，开工前对照代码）

以下几处是方案初稿没写、实现必须处理的：

1. **磁盘 blob 要用 `hash-object -w`**：`drift_paths` 用的 `hash-object --stdin-paths` 不写对象库，照抄的话 blob 不在库里，拼树才失败。
2. **替换结果不能经共享 memo 传到其他分支**：当前分支与其他分支共用一份 `memo`。不处理的话，含同一提交的其他分支会命中 memo，悄悄带上磁盘内容并被移走；而现在它们在冲突处留在原地。替换过的提交以及它之后的提交都不进 memo，其他分支保持原行为。
3. **只认文本内容冲突**：`conflict_files` 只解析 stage 行，分不出修改与删除、二进制、改名、mode 冲突。这些情况「没有冲突标记」天然成立，第 6 节最后一条也比不出意义。
4. **冲突块的模板不用 merge-tree 的冲突树**：冲突树按用户的 `merge.conflictStyle`（diff3 / zdiff3 多出 `|||||||` 段）和 `conflict-marker-size` 属性写标记，标签是 OID，文件内容里也可能有形似标记的行。改用 `git merge-file -p --object-id`（git ≥ 2.43，跟进本来就要求 2.43）对 stage 1/2/3 重新合一次，`-c merge.conflictStyle=merge` 加唯一标签，按标签切出冲突块。比对用 `-w` 写进库后读出的 blob 内容（已过 eol 过滤），不比磁盘原始字节。匹配按行贪心最左匹配 `s0 X1 s1 … Xn sn`（`Xi` 为任意内容），对这种通配模式是完备的。
5. **一次跟进里多个提交冲突**：`replay_onto` 遇到第一个冲突就返回。试重放写成循环：冲突 → 判这批文件 → 全部能用就加进替换继续 → 下一个冲突；任何一个 ✗ 整体退回。
6. **点击入口与锁内复核**：`follow()` 在基线已发布且冲突时直接返回 `NeedsManual`。新入口走「`prepare`（带替换）→ `still_valid` → `publish`」，`still_valid` 加一项「替换文件的磁盘 blob 仍是准备时那个」。替换文件必须是冲突框里列过的（点击前 SVN 又前进、冒出新冲突时，回到冲突框重新确认）。
7. **磁盘 = 新基线的连带影响**：见第 10 节问题 1。
