# 建库时可选「尊重已有的 .gitignore」——设计

> 前置：PR #90（建库前只读预检、按裁决规则分组的不一致报告、分阶段耗时）。本设计建立在它之上，
> 分支叠在它后面。spec 主文档是 `2026-09-12-svn-git-hybrid-design.md`，本文改动其 §6.3 / §6.5 的口径。

## 1. 为什么要做

用户在真实 Unity 工程（白名单 `Assets/`，扩展名 `*`）上建库被 `include_set_mismatch` 拦下：
工作副本里有一个 `.gitignore`，是用户自己**以前在这个目录里用本地 git 时留下的**，删 `.git`
时它没跟着删。它的 `*.exe` / `*.pyc` 把几百个受 SVN 版本控制的文件挡在 git 外面。

git 的优先级是「工作树里的 `.gitignore`」高于本应用生成的 `.git/info/exclude`，本应用的白名单
压不过它（2026-10-27 实测，见 PR #90 的实现日志）。从用户的角度这完全看不懂：「我让它全收，它说
有个文件挡住了」——而且报告里的 `Code/.gitignore:1:*.exe` 是 git 的格式，看不出那是一个可以去打开
的文件。

用户的判断：`.gitignore` 通常是项目规范，应当可以选择尊重；但像这次这种自己留下的旧文件，
默认应当不管它、照样把文件交给 git。

## 2. 目标 / 非目标 / 反目标

**目标**

1. 建库向导提供一个选项「尊重已有的 .gitignore 规则」，**默认不勾**。
2. **不勾**：白名单 + 扩展名说了算。实现方式是**把起作用的 `.gitignore` 改名停用**（用户已确认），
   之后 git 从根上看不到那些旧规则，所有后续功能不需要特殊处理。
3. **勾上**：已有的 `.gitignore` 说了算。被它排除的文件不交给 git 管，建库照常完成；这个选择
   **存进仓库配置**，以后「更新」「交付」「重建基线」等所有核对都按同一口径。
4. 用户在**点「建库」之前**就能看到：哪些 `.gitignore`（完整路径）的哪几行规则会挡掉多少个文件。
5. 所有提到 `.gitignore` 的报错和提示都写**完整路径 + 第几行 + 规则**，不再用 git 的
   `文件:行号:规则` 格式（用户反馈的第 1 点）。

**非目标**

- 不提供「建库之后再改这个选项」的入口。要改就重新建库（或以后另立需求）。
- 不处理全局 `core.excludesFile`：它的优先级低于 `.git/info/exclude`，本来就挡不住白名单内的文件
  （PR #90 实测）。
- 不改 `.gitignore` 的**内容**（不删行、不加反选），只整文件改名。

**反目标（做成这样就算失败，即使技术上能跑）**

- 默默改用户的文件：任何改名都必须在点「建库」之前展示、在完成页写清楚怎么恢复。
- 改动受 SVN 版本控制的 `.gitignore`：那是团队的规则，改名会变成一个要交付的 SVN 改动。
- 选了「尊重」之后，后续的体检 / 更新 / 交付里有任何一处还按「不尊重」的口径判断——表现会是把
  正常仓库误报成「基线撒谎」或「漏收」，比现在更难懂。
- 建库失败回退后，改了名的 `.gitignore` 没改回来。

## 3. 用户看到的流程

### 第 2 步「检查工作副本」

在原有 P1–P5 之外，多查一件事：有没有**起作用的** `.gitignore`。一个工作树里的 `.gitignore`
在下面两种情况下算「起作用」（用户 2026-10-28 确认）：

1. **少收**：它挡住了至少一个「SVN 里有的」W-file——即服务器期望集合（`server_expected_set`
   的口径）里的文件。只挡住未版本控制文件（本地编译产物等，SVN 里本来就没有）的 `.gitignore`
   **不算**：那些文件本来就不进基线，不会导致建库失败；改它的名反而会让这些垃圾文件全部冒进
   「本地改动」列表。受版本控制、但什么都没挡住的团队 `.gitignore` 也因此不会触发拦截。
2. **多收**：它用 `!` 反选，把用户没选的文件（扩展名不匹配）重新纳入了 git。

「挡掉 / 多收了多少个文件」都按上面的口径计数。

- 这一步还没有 `.git`。检测必须**只读**，不能在工作副本里留下任何东西（不能建 `.git`）。
  做法交给实现者；一个可行的方向是在系统临时目录建一个一次性 git 目录，用
  `--git-dir=<临时> --work-tree=<工作副本>`，把本应用将要生成的 exclude 写进临时目录的
  `info/exclude`，再批量 `check-ignore`——这样得到的裁决与建库后完全一致。
- 现有命令 `svn_preflight_check` 只收白名单、不收扩展名，而检测需要扩展名。是改签名还是新增命令
  交给实现者；改签名要按 `AGENTS.md` §7.3 前后端同步并在 `pnpm tauri dev` 里实跑。

### 第 3 步「确认并建库」

查到起作用的 `.gitignore` 时，在「建库」按钮上方列出，每个文件一块：

- 完整路径（Windows 形态，例如 `C:\…\Assets\Plugins\.gitignore`）
- 它在 SVN 里是否受版本控制
- 起作用的每一行：第几行、规则原文、挡掉多少个文件、几个样例路径

下面是勾选框「尊重已有的 .gitignore 规则」，默认不勾，旁边一句话说明勾与不勾的区别。

**没查到时不显示勾选框**，也不显示这一块。配置里记为「不尊重」（见 §4）。

### 点「建库」之后

| 情况 | 行为 |
|---|---|
| 不勾，起作用的 `.gitignore` 都**未受** SVN 版本控制 | 先把它们改名停用（§5），再照常建库 |
| 不勾，其中**有一个受** SVN 版本控制 | **不改任何文件，直接拦下**。提示：这是团队提交的规则，请勾选「尊重」，或先和团队确认。点名是哪个文件 |
| 勾上，只有「少收」 | 不动任何文件，按「尊重」口径建库 |
| 勾上，有「多收」 | **拦下**，点名是哪个 `.gitignore` 的第几行把哪些文件拉了进来。「尊重」只允许 `.gitignore` 从用户的选择里**减掉**文件，不允许往里加（用户确认，理由见 §4） |

### 完成页

- 改过名：列出每个文件的原路径和新路径，写明「想恢复就把它改回原名」。
- 选了尊重：列出「以下文件按 `.gitignore` 的规则没有交给 git 管」，按 `.gitignore` 文件和规则分组，
  给数量和样例（同 PR #90 的分组形式）。

## 4. 「尊重」是一个仓库级的持久口径

勾上之后，「哪些文件交给 git 管」（spec 里的 W-file）的定义变成：

```text
W-file = 在白名单内 ∧ 扩展名匹配 ∧ 没有被工作树里的 .gitignore 排除
```

不勾（以及没查到冲突）时与现在完全相同。

- **只做减法。** `.gitignore` 里的 `!` 反选不能把用户没选的文件加进来（用户确认）。理由：收进用户
  没选的文件比少收更出乎意料；更要紧的是，如果允许 `.gitignore` 往里加，一行 `!.svn` 就可能把
  SVN 的工作副本数据库收进 git，一次 checkout 就会损坏工作副本（spec §6.3）。所以「尊重」模式下
  遇到多收，照样以不一致拦下并点名那一行。
- 写进 `.git/mygitclient.json`，新字段（名字交给实现者，例如 `respectGitignore`），**缺省为 false**，
  这样所有已经建好的仓库行为不变。
- **选了「尊重」的仓库，配置 `version` 写成 2**；没选的仍写 1。`validate` 接受 1 和 2。这样旧版客户端
  （比如用户公司里还没升级的装机版）打开「尊重」仓库会明确报「不支持的配置版本」，而不是静默按
  「不尊重」口径工作、报出一堆看不懂的漏收。没选「尊重」的仓库新旧版本都能打开。（我的决定）
- 当前判断 W-file 的地方是纯路径函数 `is_w_file`，还有基于它的 `expected_set` /
  `server_expected_set` / `explained_paths`，以及体检、服务器集合核对、更新、交付前检查里的过滤
  （`svn_health` / `svn_server_set` / `svn_sync_in` / `svn_sync_check` / `svn_sync_out_check` /
  `svn_dirty`）。**这些地方必须全部换成同一个带 `.gitignore` 判断的口径**，不允许有一处漏掉
  （反目标第 3 条）。实现者自己决定怎么做（例如一次批量 `check-ignore` 算出被排除的集合，在一次
  操作里复用），但要有测试证明每个入口都用了它。
- **已经交给 git 管的文件，不会因为后来出现的 `.gitignore` 被移出去。** git 本身就是这个语义：
  已跟踪的文件不受 `.gitignore` 影响。所以「尊重」模式下，建库之后有人新加了一个 `.gitignore`、
  挡到了**已经在基线里**的文件，这些文件继续算 W-file。**参照统一是「当前基线树里已有的文件」**，
  所有入口一致（我的决定）。这条必须明说，因为各入口的起点不同：
  - `sync_in` / `sync_out` 的录制从 HEAD 树起步，`git add` 自然保留已跟踪文件；
  - 「重建基线」、`check_current_baseline` 的磁盘树、`svn_sync_check` 的同步前检查都从**空索引**起步，
    `git add` 会把这些文件**丢掉**。不处理的话，「体检基线」会把它们当成「基线树 ≠ 磁盘树」报
    `Lying`，「重建基线」会让基线悄悄变小，而 `work` 分支上还跟踪着它们，之后交付时表现成新增或
    「不在白名单里」。
  所以从空索引起步的入口，要把「当前基线里已有、但被 `.gitignore` 挡住」的文件显式补回候选索引，
  或者用等价的办法让口径一致。要从基线里移出它们，只能重新建库。要有用例覆盖这个形态。
- 「不尊重」模式下，以后如果又出现了起作用的 `.gitignore`（比如 SVN 更新带进来一个），沿用现在的
  行为：核对报不一致并点名那个文件。不自动改名——自动改名只发生在建库向导里、经过用户确认之后。

## 5. 改名停用的细节

- 新名字：`.gitignore.jkk-disabled`。已存在同名文件时的处理交给实现者（例如加序号），但**不能覆盖**。
- 时机：在建库的回退区里（`.git` 已被本次初始化占有之后）、`git add` 之前。**建库失败回退时，
  改过的名字必须逐个改回来**；改回失败要在错误里点名，不能静默。
- **改完要再查一遍。** git 不会进入已经被忽略的目录，那里面的 `.gitignore` 根本不会被读。例如
  `Assets/.gitignore` 写了 `Plugins/`、`Assets/Plugins/.gitignore` 写了 `*.dll`：第 2 步只会点名
  前一个，前一个改名之后，后一个才开始起作用。所以改名之后立刻按第 2 步的口径重查：
  - 如果冒出了用户在第 3 步**没看到**的起作用的 `.gitignore`，就把这次改过的名字全部改回去、
    删掉刚建的 `.git`，回到第 3 步，把新的完整清单给用户看、等用户重新确认；
  - 用户永远不会有「没看过就被改了名」的文件（反目标第 1 条）。
  - 重新确认后再走一遍，直到不再冒出新的为止。这种嵌套很少见，多数情况一次就过。（我的决定：
    第 2 步要在不写工作副本的前提下把嵌套提前算清，代价高且容易错；改名后重查更直接。）
- 完成后把改过名的文件（原路径 → 新路径）记进 `.git/mygitclient.json`，便于以后排查。
  （我的决定：完成页只显示一次，用户关掉就找不到了。）
- 被改名的 `.gitignore` 如果本身落在白名单内、扩展名又是 `*`，它是一个未版本控制的文件，
  改名后在 SVN 里仍是 `?`，不影响交付。
  - **实现时的修正（2026-10-29 真实窗口验证发现）**：svn 脏清单是改名之前读的，新名字不在
    里面；扩展名 `*` 时它是 W-file，会被当成「服务器上有」录进基线（`svn diff` 看不见未版本
    控制文件，体检拦不住）。所以改名后把新名字以 `?` 补进本次的脏清单，录制会把它剔掉。
- **实现时的修正（2026-10-29 真实窗口验证发现）**：上面「改名后重查，冒出新的就回到第 3 步」
  单独成立不了——回到第 3 步时外层已改回原名，第 2 步再查还是看不到内层，用户被反复送回。
  所以第 2 步在临时目录的影子树里**模拟**停用（只放 `.gitignore` 文件，跳过会被改名的），
  一轮轮查到不再冒出新的，把「外层停用之后才会起作用」的也列出来（标注出来）；建库时按轮
  改名，每轮冒出来的若在用户确认过的清单里就接着改，不在才全部改回、送回第 3 步。
  「不在第 2 步提前算清」那条我的决定因此作废。

## 6. 报告与提示的写法（用户反馈第 1 点）

适用于所有出现 `.gitignore` 的地方：PR #90 的不一致报告（预检与最终核对）、第 3 步的冲突列表、
完成页。

- 来源是工作树里的 `.gitignore` 时，显示**完整的 Windows 路径**（仓库根 + git 给的相对路径，
  斜杠换成反斜杠），不再只写相对路径。git 报告的是该文件的**实际位置**，可能在任意一层子目录，
  不是假设在顶层——这一点要在显示上看得出来。
- 规则写成「第 N 行 `*.exe`」，不用 `文件:行号:规则`。
- 来源是 `.git/info/exclude`（本应用生成的）时，写「本应用生成的规则」，不暴露这个路径。

## 7. 约束

- 预检和第 2 步的检测都不能写用户的工作副本；唯一允许的写操作是用户确认后的改名。
- 所有 git 调用走 `run_git` 一族封装，错误映射为 `GitError`（`AGENTS.md` §7.3）。
- 空白名单、空扩展名不能退化成「全部」（`AGENTS.md` §6.2）。
- 跨平台路径：显示用 Windows 形态，内部比较用正斜杠相对路径；大小写按 git 的 `core.ignoreCase`。
- 测试一律用一次性 fixture（SVN + git），覆盖：勾 / 不勾、受版本控制拦下、改名后回退复原、
  同名冲突、嵌套目录里的 `.gitignore`（含「外层挡住整个目录、改名后内层才起作用」的重查形态）、
  只挡未版本控制文件的 `.gitignore` 不算起作用、`!` 多收在两种模式下的处理、
  「尊重」模式下后续更新 / 交付 / 重建 / 体检不误报、已跟踪文件被新 `.gitignore` 挡到的形态、
  配置 version 2 被旧口径拒绝。
- UI 改动要在 `pnpm tauri dev` 真实窗口里验证（PR #90 的 CDP 手法可复用）。

## 8. 决定记录

**用户决定（2026-10-28）**

- 勾选框「尊重已有的 .gitignore 规则」，默认不勾。
- 不勾 = 白名单和扩展名说了算，用「改名停用」实现。
- 起作用的 `.gitignore` 受 SVN 版本控制时，不勾就拦下提示，不改名。
- 「起作用」只算挡住了 SVN 里有的文件（或 `!` 多收），只挡未版本控制文件的不算。
- 「尊重」只做减法，`!` 多收照样拦下。

**我的决定（用户可改）**

- 第 2 步检测、第 3 步列出完整清单；没查到冲突时不显示勾选框。
- 「尊重」持久化进仓库配置，后续所有核对按同一口径；参照是「当前基线树里已有的文件」，
  已在基线里的不会被后来的 `.gitignore` 移出。
- 选了「尊重」的仓库配置版本写 2，让旧版客户端明确拒绝。
- 改名后重查，冒出新的就全部改回、让用户重新确认。（实现时补充：第 2 步先在影子树里模拟停用、
  把这类提前列出，见 §5 末。）
- 改过名的文件记进仓库配置。
