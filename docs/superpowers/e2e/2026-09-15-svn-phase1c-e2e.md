## 0. 先搞清楚这套测试在干什么

### 为什么需要「fixture 仓库」

这个应用是拿来管别人的 SVN 工作副本的。测它就得**有一个 SVN 工作副本可以糟蹋**
——要在里面反复提交、回退、把目录排除掉、甚至把服务器整个改名模拟断网。

这些操作不能拿你真实的项目做。所以第一步是用脚本**临时造一个一次性的
SVN 仓库**，测完整个删掉，对你的机器不留任何痕迹。这个一次性仓库就叫 fixture。

脚本造出来的东西长这样，全都在 `%TEMP%` 底下的一个随机目录里：

```text
C:\Users\<你>\AppData\Local\Temp\phase1c_xxxxxxxx\      ← 这一整个就是「fixture」
├── repo\      SVN 服务器本体（相当于公司那台 SVN 服务器）
├── wc1\       你的工作副本  ← **应用里要打开的就是这个**
└── wc2\       「同事的机器」 ← 在这里提交 = 模拟别人改了东西
```

**「用完删掉整个 fixture」= 把最外面那个 `phase1c_xxxxxxxx` 目录整个删掉。**
脚本跑完最后一行会把删除命令连同完整路径打给你，测完复制粘贴执行即可。
忘了删也不会怎样，`%TEMP%` 本来就是临时目录，只是会占几十 MB。

### 你需要开几个窗口

| 窗口 | 干什么 | 整个测试期间 |
|---|---|---|
| **终端 A** | 跑 `pnpm tauri dev`，应用从这里启动 | 一直开着别关 |
| **终端 B** | 造 fixture、发 `svn` 命令模拟外部变更 | 一直开着别关 |
| **应用窗口** | 点界面 | 一直开着 |

`pnpm tauri dev` 会占住终端 A 不放，所以模拟外部变更的命令**必须**在终端 B 发。

### ⬜ 场景 1：打开一个普通 git 仓库（回归，不能省）

> 这期给「仓库能力」加了一个 `vcs` 字段。最容易出的回归是**普通 git 仓库被误判成
> SVN 仓库**，然后每次刷新都往后端发几个注定失败的调用。所以先拿一个普通 git
> 仓库探个路。

**做什么**

1. 应用里点 `Open Repo`（顶部标签栏）或 `Open Repository…`。
2. 随便选一个你平时用的**普通 git 仓库**（只读地看看，不会改它）。
3. 按 `F12` 打开 DevTools，切到 Console 标签。

**应该看到**

- 顶部**没有**任何黄色或红色的横幅；
- 提交框（左下角）里**没有**「仅本地，不交付」勾选框；
- 图的最底下**没有**「加载更多 SVN 历史」按钮；
- Console 里**没有** SVN 相关的报错或警告。

**看到别的说明什么**

出现上面任何一样，就是 git 仓库被误判成了 SVN 仓库。这条不通的话后面都别测了，
直接告诉我。

### ⬜ 场景 2：打开 fixture，走完初始化向导

**做什么**

1. `Open Repo` → 选 `<fixture>\wc1`。
2. 应用会认出这是个「还没交给 git 管」的 SVN 工作副本，自动弹出向导，
   标题是 **「把这个 SVN 工作副本交给 git 管」**。
3. 第一栏「**交给 git 管的目录（一行一条）**」——把默认内容清空，填一行：

   ```text
   Code/
   ```

4. 第二栏「**收哪些扩展名**」——填：

   ```text
   .cs
   ```

5. 点 **「检查工作副本」** → 点 **「下一步」** → 点 **「建库」** → 点 **「关闭」**。

**应该看到**

- 「检查工作副本」之后显示 **检查通过**，并列出 `记账 revision：r1`、仓库根、UUID；
- 「建库」之后显示 **建好了**、`首个基线：r1(...)`、
  `当前分支已切到 work，基线分支是 svn/base`；
- 还会多出一条绿色/中性的 **「基线已通过体检（r1）」**；
- 关闭向导后，图里出现**一行 SVN 提交**：它在平时显示短 hash 的位置显示
  **`r1`**，颜色与普通 git 提交不同；
- 顶部**没有**警告横幅，但**有**一条灰色的细条，写着
  「revision 对得上不代表基线记的内容是对的……」外加一个 **「体检基线」** 按钮。

**看到别的说明什么**

- 向导报错 → 把错误原文抄下来；
- 图里没有 `r1` 那一行 → 这是本期最大的一处修复（trailer 传递），说明没修好；
- 那条灰色细条不出现 → 常驻体检入口没生效。

### ⬜ 场景 3：同事提交了东西，你这边怎么表现

> 这条要验的是**分两段**的：同事提交完、你还没 update 的时候**不该**报警；
> 你 update 之后才该报警。很多人会以为一提交就该亮红，那是错的。

**做什么（第一段）**

终端 B：

```powershell
Set-Location "$fx\wc2"
svn update --non-interactive
Set-Content "Code\Deep\D.cs" -Value 'class D { int y; }' -NoNewline
svn commit -m "r2 外部改深层文件" --non-interactive
```

回到应用窗口，随便在 `<fixture>\wc1` 里存一下某个文件（或者切走再切回这个标签），
触发一次刷新。

**应该看到（第一段）**

**什么横幅都不出现。** 因为你的工作副本还停在 r1，和基线一致。

**做什么（第二段）**

终端 B：

```powershell
Set-Location "$fx\wc1"
svn update --non-interactive
```

再回应用触发一次刷新。

**应该看到（第二段）**

- 一条**红色**横幅，标题 **「基线落后于工作副本」**；
- 文案里提到 r2 和 r1；
- 横幅上有 **「重建基线…」** 和 **「体检基线」** 两个按钮；
- 底下一句说明：重建基线不会碰工作目录、也不会推进你的工作分支。

**看到别的说明什么**

- 第一段就亮红 → 判据用错了（不该拿工作副本根的 revision 当判据）；
- 第二段说的是「工作副本被回退到了基线之前」→ **方向反了**，这正是这轮修的
  一个 bug（serde 字段名对不上），说明没修好；
- 文案里出现 `rundefined` 或 `r undefined` → 同上，同一个 bug。

### ⬜ 场景 4：点「重建基线」

> ⚠️ **前提：白名单内的 `svn status` 必须是干净的**，否则会被拒绝。
> 这是一条**已知的设计限制**，不是这条用例的 bug —— 见文末
> 「已知问题：重建基线在真实开发节奏下点不动」。
> 场景 3 做完时白名单还是干净的（`svn update` 不产生本地修改），
> 所以**按顺序做**就能测到。要是你中途自己加过文件或改过白名单内的东西，
> 先在终端 B 跑 `svn status Code` 看一眼。

**做什么**

1. 先记下**重建之前**的工作区状态。终端 B：

   ```powershell
   Set-Location "$fx\wc1"
   git status --short          # 记下这几行，等会儿要对比
   Get-FileHash "Code\Deep\D.cs" | Select-Object -ExpandProperty Hash
   ```

2. 在场景 3 那条红色横幅上点 **「重建基线…」**。
3. 读一遍弹出来的确认框，然后点 **「重建」**。
4. 再跑一遍同样的命令，外加：

   ```powershell
   git status --short
   Get-FileHash "Code\Deep\D.cs" | Select-Object -ExpandProperty Hash
   git branch --show-current
   ```

**应该看到**

- 确认框里写明「不会修改工作目录里的任何文件，也不会推进你的工作分支」；
- 确认后红色横幅**消失**（回到场景 2 那条灰色细条）；
- **`git status --short` 前后两次输出完全一样** —— 重建不碰工作区；
- `Code\Deep\D.cs` 的哈希前后一致 —— 文件内容没被改回去；
- `git branch --show-current` 仍然是 `work`。

> 📌 这里**大概率会看到 ` M Code/Deep/D.cs`，那是正常的**，不是 bug。
> 场景 3 的 `svn update` 把磁盘换成了 r2 的内容，而你的 git 工作分支上最后一个
> 提交记的还是 r1 的内容，git 当然认为这个文件被改了。
> 这条要验的是「重建**没有改变**工作区」，不是「工作区是干净的」。

**看到别的说明什么**

- 前后两次 `git status` 不一样、或者文件哈希变了 → 重建碰了工作目录，
  **严重问题，立刻停下来告诉我**；
- 分支从 `work` 变了 → 同上；
- 弹出 `[svn_preflight_dirty] 白名单内的工作副本不干净` → 见文末的已知问题，
  不是这条用例的失败。

### ⬜ 场景 5：点「体检基线」的三种结果

> 「体检」= 拿基线记的内容跟服务器上那个 revision 逐个文件比一遍。
> 它有**三种**结果，三种都要见到 —— 尤其要确认「没能验证」和「验证不通过」
> 是分开的两回事。

**5a 正常**

点灰色细条上的 **「体检基线」**。

应该看到弹框 **「基线已通过体检（rN）」**。

**5b 连不上服务器**

终端 B：

```powershell
Rename-Item "$fx\repo" "repo_off"
```

再点一次 **「体检基线」**。

应该看到 **「基线未经体检」**，并说明原因（连不上）。
**不能**说成「基线有问题」——那是两回事。

测完改回来：

```powershell
Rename-Item "$fx\repo_off" "repo"
```

**5c 磁盘和基线对不上**

终端 B：

```powershell
Set-Location "$fx\wc1"
Add-Content "Code\A.cs" -Value "// 本地随手改的"
git add Code/A.cs
git commit -m "只提交到 git，不提交到 svn"
```

再点 **「体检基线」**。

| 你测的是哪个构建 | 预期 |
|---|---|
| **1c**（`feat/svn-phase1c`） | **「基线未经体检」**，**不是**「基线与服务器不符」 |
| **B**（`feat/svn-baseline-from-server`，2026-09-17 之后） | **「基线已通过体检（rN）」** ← 预期已改，不是 bug |

> 1c 为什么是「没验成」：这时磁盘内容已经和基线树不一致了，体检的前提不成立，
> 所以它诚实地说「没验成」而不是硬给一个结论。
>
> B 为什么变成「通过」：那道前提正是本文末「已知问题」那一节要修的东西之一——
> 程序员的工作区 99% 的时间都是脏的，前提永远不成立，这颗按钮就永远只会回答
> 「没法下结论」，等于不存在。B 把判据换成 spec §6.8.7 的 `D \ S == ∅`：
> `Code/A.cs` 这处改动落进 `S` 被解释掉，其余文件与服务器逐一对得上 → Verified。
>
> ⚠️ **代价要说清楚**：`S` 里的那些文件，这条检查**什么也没证明**。要让体检覆盖
> 全部文件，工作副本必须是干净的——B 那份清单的场景 9 / 10 正是成对测这件事的。

做完把内容改回去，让磁盘重新和基线一致：

```powershell
Set-Content "Code\A.cs" -Value 'class A {}' -NoNewline
git add Code/A.cs
git commit -m "改回去"
```

> 这里**故意不用** `git reset --hard`。它确实更直接，但把破坏性命令写进照抄式的
> 文档里，只要有一次粘贴时目录不对，毁的就是别的仓库。多一个提交无所谓。

改回去之后再点一次「体检基线」，应该又回到 **「基线已通过体检（r1）」**。

### ⬜ 场景 6：把一个白名单子目录排除掉

> 这条测的是这期补的一个盲区：`svn update --set-depth=exclude` 之后，
> SVN 那边**所有检查都显示正常**，而服务器上确实存在的源码文件在你本地根本没有
> ——git 以为自己在保护它，其实没有。唯一能看见它的办法是拿服务器的文件清单
> 对一遍。

**做什么**

终端 B：

```powershell
Set-Location "$fx\wc1"
svn update --set-depth=exclude --non-interactive -- "Code/Deep@"
```

> `Code/Deep@` 末尾那个 `@` 不能省。SVN 会把最后一个 `@` 之后的内容当版本号解析，
> 加一个空的 `@` 才表示「就是这个路径本身」。

回应用里**切出去再切回来**：点一下别的窗口（比如终端 B），再点回应用窗口。

> ⚠️ **存个文件或切标签不管用**（本文最初写的就是那句，是错的）。服务器侧核对
> 要走网络，不能挂在文件监听那条通道上——那条通道一次保存就触发一次
> （`refreshPullRequests` 的注释里记的是同一条理由）。
>
> 2026-09-19 之后它的触发点是这四个：
>
> | 触发点 | 限频 |
> |---|---|
> | 打开仓库 | 无 |
> | 点过「重建基线」之后 | 无 |
> | **窗口重新获得焦点** | 距上次核对满 1 分钟才跑 |
> | **每 5 分钟一次的定时器** | 同上 |
>
> 所以：切回来**没反应**时，先看是不是一分钟内刚核对过（比如你刚打开仓库）。
> 等一分钟再切一次，或者干脆等定时器那一次（最多 5 分钟）。
> 代码位置：`src/store/repoStore.ts` 的 `auditSvnIfDue` 与同文件末尾那个
> `useEffect`；限频判据在 `src/engine/svnSync.ts` 的 `auditIsDue`，有 vitest。

**应该看到**

- **失同步横幅不出现** —— 这是设计如此，不是 bug（那套判据看不见 depth-exclude）；
- 但出现一条**黄色**提示 **「服务器上有代码文件不在本地」**，
  列出 **`Code/Deep/D.cs`**，并说明 git 没有在保护它。

**看到别的说明什么**

- 黄条里还列了 `Code/Art.psd` 或 `Art/boss.psd` → **误报**。那两个本来就不该进 git，
  报出来就是噪音；
- 黄条根本不出现 → **先确认触发点**（见上面那条 ⚠️）：切窗口有一分钟的限频闸。
  最稳的办法是把仓库关掉重新打开——那一次不限频。仍然不出现才是机制没生效。

做完恢复：

```powershell
svn update --set-depth=infinity --non-interactive -- "Code/Deep@"
```

### ⬜ 场景 7：服务器连不上时打开仓库

**做什么**

1. 关掉应用里的这个仓库标签。
2. 终端 B：`Rename-Item "$fx\repo" "repo_off"`
3. 应用里重新 `Open Repo` → `<fixture>\wc1`。
4. 看 DevTools 的 Console。

**应该看到**

- 图**仍然能画出来**（用的是本地缓存的 SVN 历史）；
- 顶部**不弹红色错误横幅**；
- Console 里有一条 `console.warn`，大意是「拉取 SVN 历史失败，图上只显示缓存里
  已有的部分」;
- 黄色的漏收提示**不出现**（连不上时它的结论是「没验成」，不打扰你）。

**看到别的说明什么**

顶部弹出红色错误横幅 → 一条锦上添花的后台请求把主错误位置占了，
真正重要的错误以后就会被它盖住。

测完改回来：`Rename-Item "$fx\repo_off" "repo"`

### ⬜ 场景 8：「加载更多 SVN 历史」——**这条最重要，别只看按钮**

> 这轮改动最大的一块。它修的缺陷是：翻页时**中间整段历史被永久跳过**，
> 而界面上只表现为「图里少了些节点」，不报任何错。
>
> ⚠️ **坏的实现和好的实现，都表现为「点一下按钮就变灰」。**
> 只盯按钮完全分不出来，必须去数节点。

**做什么**

## 已知问题：重建基线在真实开发节奏下点不动

> **✅ 已在 `feat/svn-baseline-from-server` 分支上修掉**（2026-09-17，走方案 B）。
> 修法：干净文件仍从磁盘录，**脏文件改取 `svn cat -r BASE` 的字节**，`A` / `?`
> 从基线树里剔除；体检判据同步推广成 `D \ S == ∅`。spec 的 §6.5 P1、§6.3.1、
> §6.8.7、§16.1、§16.2 都已改。
>
> **本节原样保留，不要删。** 它是那次修改的全部理由——现象、根因、以及「为什么
> 不能简单地放行」这三段，正是新做法必须绕开的那些陷阱。下面「出路」那张表里的
> A / B / C 也保留：将来若有人想换回 A 或 C，得先看见当初为什么没选它们。
>
> ⚠️ 这一节描述的行为属于 **Phase 1c 这个 PR**。如果你测的是 1c，下面写的仍然是
> 你会看到的现象；如果你测的是 B 那个分支，整套步骤改看
> `docs/superpowers/e2e/2026-09-18-svn-baseline-from-server-e2e.md`。

**2026-09-17 由用户在手工测试中发现并实测确认。这是设计缺陷，不是用例写错。**

### 现象

白名单内 `svn status` 只要不干净，「重建基线」就被
`[svn_preflight_dirty]` 拒绝。而**只要你干过活，它就一直不干净**：

```text
改一个文件 → git add → git commit
  git status  →  ""              ← git 侧干净，活已经提交了
  svn status  →  "M  Code\A.cs"  ← SVN 侧仍然脏
```

git 和 SVN **共用同一个工作目录**。提交到 git 只是把改动记进 git 的对象库，
磁盘上那个文件相对「SVN 上次更新时的内容」依然是已修改。所以对一个正在写代码的
人来说，白名单几乎永远是脏的。

于是形成死胡同：同事提交 → 你 `svn update` → 红色横幅让你「重建基线」→
**点了被拒绝**，而你除了把手头的活全部交付掉之外没有别的出路。

### 根因

基线 commit 的 trailer 声称「这棵树 == 服务器上的 rN」。而现在这棵树是
**照着磁盘录的**（spec §16 的 R2：`git add -A` 白名单路径）。
只有当磁盘 == 服务器 rN 时这句声称才成立 —— 也就是白名单干净的时候。
**那道干净检查不是多余的洁癖，它是「照磁盘录」这个做法的必要条件。**

spec §16 把这个前提写成了事实：「此时 `svn status` 干净，意味着磁盘上白名单内的
内容**已经就是**新的服务器内容」。这句话在「外部 update 且我手上没活」时成立，
在日常开发节奏下不成立。

### 为什么不能简单地放行

如果带着本地修改录基线，基线里就含进了服务器上不存在的内容。后果不是界面难看，
而是 **Phase 3 交付时按「工作分支 vs 基线」算改动集，你自己那些改动会被算进基线、
从交付集合里悄悄消失** —— 你以为交付了，实际没有。
所以现在这个「拒绝」虽然难用，但方向是对的：宁可挡住，不可撒谎。

### 出路（待定，需要决定）

| 方案 | 做法 | 代价 |
|---|---|---|
| A 从服务器录 | `svn export -r N` 整个白名单，拿它录基线 | 每次重建都重下整个白名单，大工程上很贵 |
| B 只补脏文件 | 照磁盘录，但把 `svn status` 报脏的那些文件换成 `svn cat -r N` 的内容 | 只为脏文件付网络代价；但 §6.8 体检也要跟着改（它现在比的是服务器 vs **磁盘**） |
| C 维持现状 | 把限制写进 UI，横幅上不要再推荐一个点不动的按钮 | 核心收益在日常节奏下仍然拿不到 |

**这三条都超出 Phase 1c 的范围**（A/B 要改基线录制方式与 §6.8 体检，
等于动 spec §16 和 §6.8），所以本 PR 不动它，先如实记录在这里。

**2026-09-17 决定：选 B，另开分支 `feat/svn-baseline-from-server` 实施。**
A 被否是因为大工程上每次重建都重下整个白名单太贵；C 被否是因为它只是把死胡同
写进 UI，§6.4 那个「我相对上次更新改了什么」的核心收益在日常节奏下仍然拿不到。

> ⚠️ **下面这张表记的是当时用 `-r N` 测出来的结论，实现最终改用了 `-r BASE`**
> （`-r N` 需要联网，`-r BASE` 走本地 `.svn/pristine`）。换了参数形式之后 B3 那条
> 的错误码也跟着变了：`-r N` 报 `E195002`，`-r BASE` 报 `E200009`。

| # | 问题 | 实测结果 |
|---|---|---|
| B1 | 能不能不碰磁盘拿到服务器那一版？ | ✅ `svn cat -r N <path>@` 对**已本地修改**的文件返回服务器内容，磁盘不变 |
| B2 | 被 `svn delete` 掉的文件呢？ | ✅ 照样返回服务器内容（磁盘上已经没有这个文件了） |
| B3 | `svn add` 未提交 / 未纳入版本控制的呢？ | ✅ `svn cat` 报 `E195002: has no committed revision` —— 明确可判，按「服务器上没有」从树里剔除 |
| B4 | `svn:eol-style=native` 会不会让两条来源的换行不一致？ | ✅ **不会**。实测磁盘 = `svn cat`(工作副本) = `svn cat`(URL)，三者字节完全相同（Windows 上都是 CRLF）。`svn cat` 自己做 eol 转换 |

### 体检新判据 `D \ S == ∅` 的实测

```text
D = svn diff --old=<url>/Code@N --new=Code --summarize   （磁盘 vs 服务器 rN）
S = svn status --no-ignore --ignore-externals            （磁盘 vs 上次更新）
判据：D \ S 必须为空
```

**不误报**（工作副本停在 rN、手上有四种脏）：

```text
D = {A.cs, Added.cs, B.cs}
S = {A.cs, Added.cs, B.cs, New.cs}
D \ S = {}                    ← 本地改动不会被判成「基线撒谎」
S \ D = {New.cs}              ← 未纳入版本控制的，svn diff 不报，符合预期
```

**有牙齿**（基线声称 r2、而磁盘其实停在 r1 —— 真正要防的撒谎形态）：

```text
svn status        →  {}                              ← 看不见（相对 r1 确实没改）
svn diff vs url@2 →  {A.cs[item=modified]}           ← 看得见
D \ S = {A.cs} ≠ ∅                                   ← 判据成立并报警
```

### ⚠️ 一个**已存在**的盲区，不是 B 引入的

试着构造「同长度篡改一个字节 + 还原 mtime」时：

```text
svn status  →  看不见
svn diff    →  **也看不见**
```

svn 靠 大小 + mtime 走捷径，两条命令都被绕过。也就是说**今天的 §6.8 体检
同样看不见这种篡改**——这个盲区不是 B 带来的，B 也不会让它变糟。
它的威胁模型（有人精确地同长度改字节再把时间戳改回去）不现实，
记在这里只是为了别把体检的能力说得比实际强。
