## 决策条目

### 偏离计划

- 6.5 的第二项「本地这边是不是只是 SVN 某个旧 revision 的快照」没有单独做：PR 121 已经把「与更新的某个基线逐字节相同」的内容在重放时直接换成基线版本，冲突里不再有它们；剩下的情形要联网才判得了。
- 6.7 只改文案、不加新按钮：手动跟进必须先经过一次对象层跟进（它负责发布基线、算冲突、给出 6.10 的清单），直接入口会绕过这些。报告里列的两条路之一（在横幅上写明路径），按它做。
- 6.8 的两档按 hunk 判定：所有 hunk 都是 `present` 算「已确认在 SVN 上」，有任何 `unknown` 算「拿不准」。

### 计划没写的坑

- merge-tree 冲突时 stdout 的第一个字段同样是树 OID，冲突文件以带冲突标记的内容写在里面，可以直接 `cat-file blob <tree>:<path>` 取预览，不用再跑一次合并。
- merge-tree 的冲突标签是传给它的 OID。重放时「我们这边」是新基线、「他们那边」是被重放的 commit，与 rebase 相同：11-05 用户用外部合并工具时就弄反过，所以预览里把标签换成「新基线（SVN）/ 你的提交」。
- `Target::Conflict` 与 `NeedsManual` 的字段已经要在四处来回抄，抽成 `ManualNeeded` 一个结构。

### 为什么这么改是安全的

- 全部只读：SVN 侧的作者与 revision 来自录基线时已有的外部变更清单，不额外跑 svn；预览只读 git 对象，读失败或二进制、超过 512KB 时只是没有预览。预览只取前 5 个文件。
- 冲突树没有 ref 指着，与重放产生的其他对象一样由 gc 回收。
- 前端对旧后端缺少 `details` 时照原样列文件名。
