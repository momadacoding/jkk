## 决策条目

### 偏离方案

- 方案 §5 列了「退回到分支自己基线版本的改动不按本规则换」的端到端测试。改成直接测 `SnapshotRule::paths`：退回旧版本那条 commit 在端到端里的结局（冲突或不冲突）有没有这条规则都一样，测不出区别。
- Local-Only 同上，并入同一条规则级测试。

### 计划没写的坑

- **master 上 `cargo clippy --all-targets` 本来就过不了**：PR 119 新加的 `tests/svn_follow_audit.rs` 没有测试文件惯用的 `#![allow(clippy::unwrap_used, clippy::panic)]`，PR 118 的 lint 护栏随后合入，两者一碰就报错。本 PR 补上这一行（与其他测试文件相同），否则 §5.2 的门槛过不了。
- 手动跟进不能只靠对象层：对象层重放把快照内容换掉之后，冲突只剩真冲突，用户点「手动跟进」，原来的 `rebase <新基线>` 又会原样 pick 快照提交，35 个冲突在磁盘上回来。所以手动跟进必须用同一份规则改 todo。
- `rebase -i` 的 todo 必须只写 OID：`rebase.instructionFormat` 会改说明文字，pick 只认第一个字段。
- 合并结果按「两条规则都命中算 F2 ①」分节：那是我自己的提交，「你已经提交到了 SVN」比「多半是快照」更准。

### 为什么这么改是安全的

- 本规则只往 F2 ① 已有的 `superseded` 集合里加路径，重放引擎、索引拼装、发布流程一行没改。被换掉的是 commit 里与某个较新 SVN 版本**逐字节相同**的内容，换成的是同一路径在 NEW 上的版本：NEW 要么就是那个版本，要么是它之后 SVN 上的演进。丢不掉 SVN 上没有的东西。
- 换的手段是写回 C^ 的条目，所以还要求 C^ 的条目也是纯 SVN 的（review 第 1 条）：这样写回去的东西本身就不含我的内容，merge-tree 再取 NEW 的版本。
- 唯一会丢的情形是用户有意停在某个比分支基线新、比 NEW 旧的 SVN 版本，报告单独列出（`snapshot` 节，提示从原 commit 取回）；手动跟进在冲突框里提前列出。原 commit 在 reflog 里。
- 退回到分支自己基线版本的改动不算命中（`read_versions` 去掉与 scope 相同的条目）；Local-Only 不命中。
- 判定出错时这条 commit 不命中，退回原行为（多一个冲突，不会合错）。
- 手动跟进：继续、放弃、冲突出口仍是 `git rebase` 自己的状态机；C' 只是对象，没有 ref 指着，放弃时 `rebase --abort` 回到原分支（测试覆盖）。todo 在写 journal 之前算好、一起落盘，崩在 rebase 之前时继续用同一份。
- drift 只告警不拦：按分析 §6.12，手动点「跟进」时这种情形可以完成，问题是原来不提示。

### 独立 review 第 1 轮（opus subagent）

没有高危。

| 级别 | 发现 | 处理 |
|---|---|---|
| 中 | 命中路径换回的是 C^ 的条目：C^ 里有我自己的内容时（前面的 commit 改过、后来 SVN 侧撤掉再整包提交），撤掉的改动被复活，报告还说采用了新基线；其他分支上完全静默。原「为什么安全」的论证在这种情形下不成立 | 规则加第 2 条：C^ 的条目也必须是纯 SVN 的（等于分支基线或出现在更新的基线里），否则不命中。补规则级测试 |
| 中 | 手动跟进换掉了路径却完全不报告 | `NeedsManual` 新增 `snapshot`，冲突框在**动手之前**列出。「切换并手动跟进」入口不经过冲突框，仍不列，见遗留 |
| 中 | 纯快照 commit 在手动跟进里变成空 commit 留在历史里（rebase 保留一开始就为空的 commit） | C' 与 C^ 同树时不放进 todo，一个不剩时用 `noop`。补测试，变异验证确认了 git 确实会留下空 commit |
| 低 | drift 判据分不清「合错」与「磁盘上撤了已提交的改动」；测试输入恰好是后一种 | 文案改成「对不上，请核对」，列出两种可能；测试换成「我交给 SVN 之后同事又改」的真实形状 |
| 低 | 只改 mode 会误报 drift | 要求 blob 不同 |
| 低 | drift 出错会让整个跟进失败 | 出错只记日志 |
| 低 | 内容已经等于 NEW 也进 snapshot 节、把结局标成 attention | `reported_paths` 去掉它们，既不进 snapshot 也不进 rewritten；补测试 |
| 低 | 规则只认有基线 commit 的版本 | 方案 §2 写明边界 |
| 低 | todo 放环境变量有长度上限；C' 没有 ref，搁置太久会被 gc | 超过约 650 个 commit 退回原样 rebase；rebase 前 `cat-file --batch-check` 核对，丢了就报错提示放弃重来（不挂 ref：要在收尾、放弃、崩溃恢复三处清理，代价大于收益） |
| 低 | `read_versions` 整棵 `ls-tree -r` | 改成只查用到的路径、分批。每个基线一次 `diff-tree` 不改：基线数通常是个位数 |

review 指出的测试缺口里，「其他分支按自己的基线命中」没补：`plan_others` 只挪包含上一个基线的分支，它们的基线到 NEW 之间只有 NEW 一个基线，规则命中时内容必然等于 NEW，换不换都一样，端到端测不出区别。
