## 3. 各项做法

### 3.1 A：报告文案

- 没放回的补丁：和下面的放回框合成一节，标题改成「要不要放回这 N 个文件的 Local-Only 补丁？」。原因只写一次：SVN 上最后改它的是别人，jkk 分不清补丁是不是你有意去掉的。每个文件后面只写补丁来自哪个提交、SVN 最后提交者。
- 分支与磁盘对不上：说明压成三句：是什么（这些文件分支里的内容和 SVN 版本不同，「本地改动」里会出现它们）、怎么办（磁盘是对的就提交进分支）、例外（差的是 Local-Only 补丁时别提交）。
- 泄漏告警：泄漏所在提交在 `dropped` 里时，标「已从分支移除：内容都在 SVN 上了」，不再显示成还在分支上。
- 涉及文件：`src/engine/svnFollow.ts`（`describeFollowReport`、`leakSection`）、报告组件、`tests/vitest/`。

### 3.2 B：写清差几行、是谁造成的

- 后端在算 drift 的同一处，对每个文件用 libgit2 统计分支版本与磁盘版本的增删行数；磁盘内容按 `git add` 的过滤规则取，与 `drift_paths` 同口径（见 §8.1：不用读磁盘）。
- 造成差异的提交复用 `retained_by_path` 已有的结果（重放后仍保留、改过该文件的提交）。
- `FollowReport` 新增字段；旧后端没有该字段时前端按原样显示。

### 3.3 C：只读调用改 libgit2

- `svn_replay.rs` 的 `commit_like` 里每个提交一次 `git log -1`（本次 11 次，0.9 s）。
- `svn_replay.rs` 与 `svn_snapshot.rs` 的 `git ls-tree`（9 次，0.7 s）。
- `svn_replay.rs` 的 `git rev-parse <c>^{tree}`，以及跟进路径上的 `diff-tree`、`merge-base --is-ancestor`、`rev-list`（约 12 次，0.8 s）。
- 写操作（`merge-tree`、`commit-tree`、`update-ref` 等）保持走 git CLI，符合项目「读走 libgit2、写走 git CLI」的约定。

### 3.4 D：提交被 git 自动维护卡住（暂不做）

- 原因：跟进每次都写大量松散对象（`git add -A`、`svn cat`、`merge-tree`），所以 `git commit` 结尾的自动维护经常被触发，Windows 上它在前台跑完才返回。
- 做法：jkk 提交时带 `-c maintenance.auto=false`；提交返回后在后台跑一次 `git maintenance run --auto`，不挡界面。说明框在提交成功后立刻清空，不等刷新（再省约 1.4 s）。
- 待定：merge、rebase、cherry-pick 等同样会触发自动维护的写操作是否一并处理。

## 7. 补充：跟进里的 svn diff 核对为什么慢（2026-11-16 实测）

结论：不是服务器慢，是本地逐个文件的开销。核对要过 23 个白名单目录里全部 40,331 个受 SVN 管理的文件，
基线只用到其中 17,834 个。

| 测量（只读，Client 仓库） | 结果 |
|---|---|
| 网络往返：`svn info URL` | 0.15 s |
| 跟进用的原样命令 `svn diff --old=URL@68650 --new=. --summarize`（跑两次） | 14.8 s；svn.exe 自身 CPU 14.1 s，其中内核 12.9 s，说明不是在等服务器 |
| 同样 23 个目录的 `svn status` | 1.4 s |
| Packages（9,651 个文件）单独 `svn diff` | 2.1 s，内核 1.9 s |
| Packages：Python 逐个打开并读 4 KB | 2.7 s，内核 2.0 s（每个文件 0.21 ms） |
| Packages：只列目录 | 0.14 s（每个文件 0.01 ms） |

- 为什么 status 快、diff 慢：`svn status` 靠列目录拿时间戳；`svn diff` 每个文件的开销相当于打开并读一次文件。具体是读文件还是逐个查 wc.db（122 MB），没有 Process Monitor 证实不了。
- 这台机器打开文件格外贵：Defender 实时防护是关的，但装着别的文件过滤驱动（sysdiag、sfaioguard / sfaioctrl、file_filter、load_driver）。没法关掉它们做对照，「是它们拖慢的」只是推测。
- 扫了大量不用的文件：Assets/Test 1,808 个只用 4 个；Audio 843 个只用 2 个；Assets/Plugins 5,083 个用 1,167 个；Packages 9,651 个用 3,605 个。
- 波动：跟进时这条命令 7.4 s，事后单独跑两次都是 14.8 s，原因没查到。

换参数的实测（同一时段连续跑，结果都和原命令一致）：

| 做法 | 耗时 |
|---|---|
| 原命令：一条命令带 23 个目录 | 14.8–15.8 s（4 次） |
| 23 个目录各跑一条，顺序 | 9.9 s |
| 23 个目录各跑一条，4 个并行 | 8.0 s（8 个并行 8.1 s） |
| 只比含基线文件的 79 个子目录，一条命令 | 9.9 s |
| 把基线文件路径当参数 | 每个路径约 11 ms（300 个 3.55 s），17,834 个约 200 s；`svn diff` 不支持 `--targets` |

- 合并命令有额外开销：Packages + Tools 合成一条 5.26 s，分开跑 3.4 s。原因在 svn 内部，没查。
- 并行几乎没用：最大的目录 Packages 单跑 2.1 s，但 4 个、8 个并行总共都要 8 s，进程在内核里互相等。
- 当初为什么合并：2026-11-09 合并这条命令时依据的「逐目录 33.3 s」来自 11-07 一次约 200 s 的跟进（979 个子进程同时在抢资源），合并之后没有做过对比测量。

可选方向（未排期）：把体检的 floor diff 改回每个目录一条（顺序或 4 个并行），今天实测快 36–49%，结论不变。
风险：连服务器慢的时候，23 次连接的开销可能把优势吃掉，改之前要在慢的时段再测一次。

## 8. 对照代码的修正（2026-11-17）

### 8.1 B 比上面写的简单

- **造成差异的提交已经在报告里**：后端把整个 drift 并进了 `overlap`（`overlap_files` 先取 `retained_by_path`，再补上 drift），`overlap[].commits` 就是这些提交。原来只是前端 drift 那一节没显示。A 顺手把它显示出来（见 decisions 的 A-偏离 1），B 只剩行数。
- **行数不用读磁盘**：一个文件进 drift 的条件就是「磁盘按 `git add` 过滤后的 hash == 新基线的 blob」（`drift_paths`）。所以分支相对磁盘差几行 = blob(新基线) 对 blob(tip)，两边都在对象库里，libgit2 直接比。§5 里 autocrlf 那条风险不存在。估时约 2–3 小时。

### 8.2 C 要先补 fixture

PR 179 是在 2 万文件 fixture 上量的，那里分支上没有要重放的提交；这次 11 个提交，每个提交一次的
`log -1`、`rev-parse ^{tree}`、`ls-tree` 才冒出来。先给 bench fixture 加约 10 个改外部文件的分支提交，
否则「性能日志里这些进程消失」只能在 Client 仓库上验。`commit_like` 的 `--date=raw` 与说明编码要逐字节等价，
沿用 PR 179 的 `or_cli`：认不出的形状退回 git。

### 8.3 A 还要改自动跟进被挡时的横幅

自动跟进被条件 8 挡下时，横幅上是后端的 `svn_auto_follow_leak` 文案（「可能已经被带上了 SVN 服务器」），
只改报告不够。条件 8 本身不变：泄漏要第一时间知道，而且这次即使不算已丢弃的提交，「editor 便利性优化」仍在泄漏。

### 8.4 收益最大的是 §7，D 的风险表少一条

- §7 的 floor diff 改回逐目录，能省约 5 s，是 C 的两倍。按 §7 的风险，先在服务器慢的时段再测一次，再定排在 C 前还是并行。
- D 的后台维护与 jkk 自己的写操作并发会撞锁，失败的会是用户的操作而不是维护。以后做 D 时要么在跟进 / 提交的同步锁里跑，要么跑之前确认没有进行中的写操作。
