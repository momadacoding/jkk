# 部分自动跟进（E）

来源：使用报告 2026-11-12 第 5.5 节「第二阶段：部分跟进（E）」，A～D 已随 PR 160 合并。

## 问题

自动跟进是全有或全无：`auto_blocker` 只要有一个文件不满足条件就整次跳过，280 个能跟的文件跟着一起等。新基线由 `record_from_old_base` 按整个工作副本一次录制，没有排除个别文件的口子。

## 做法

只改自动跟进（`follow_auto`）。横幅上的「跟进」按钮仍是整次跟进：用户点了，就是要看全部结果、走冲突出口。

1. 照常准备一遍（`prepare`），`auto_blocker` 拦了，再看拦的原因能不能按文件排除。
2. 能排除时，用**第一遍录好的** `Recorded`（不再联网体检一次）造一个部分基线：被排除的文件取旧基线里的内容（树条目）和 revision，其余文件跟到新 revision。
3. 按部分基线再准备一遍（重放、核对、泄漏），再判断一次；仍然被拦，就像现在一样整次不做，横幅写**第一遍**的原因。
4. 发布、journal、崩溃恢复都不变。锁内复核（`still_valid` 的 R3c）按同样的覆盖规则重算映射。

### 能按文件排除的原因

| 拦截原因 | 处理 |
|---|---|
| 重放结果和磁盘对不上（overlap 里 `matches_disk = false` 且不会自动放回） | 排除这些文件 |
| 重放冲突（`Target::Conflict`） | 排除冲突文件 |
| 磁盘上还是分支的旧内容（`stale_disk`） | ~~排除这些文件~~ 整次拦（独立 review 中 2：它看的是分支落后那段，留下也照样报，见决策日志） |
| 泄漏告警 | 排除泄漏的文件。不跟进，横幅一直挂着，提醒作用还在 |
| 没能向服务器核对、核对本身出错、仓库一直在变、分支落后 | 仍然整次拦 |

### 只排除「外部修改」的文件

被排除的文件必须在旧基线树和新录的树里都存在（外部修改）。外部新增、外部删除的文件出现在拦截原因里时，整次拦。这样报告里列的三个风险都不会出现：

- SVN 改名 = 删 A + 加 B：两者都不是「修改」，排除不了，整次拦，不会只跟一半；
- SVN 删了目录、目录里有文件要排除：要排除的文件本身就是删除，整次拦；
- 一个 commit 同时改到排除和不排除的文件：基线按文件记 revision，被排除的文件留在旧 revision，分支 commit 照常重放到部分基线上，第二遍再判断一次。

排除之后没有剩下要跟的文件（所有外部变化都被排除）时，整次拦。

### 部分基线的映射

用 `compute_map` 重算：节点状态里被排除文件的 `node_rev`、`commit_rev` 都换成旧基线映射里它的 revision。floor 因此可能降低，此时原来按 floor 不单列的文件会按 `commit_rev > floor` 的规则单列，记账规则不变。floor 降低时按部分基线再体检一次，让新 floor 与原 floor 之间删掉的文件由服务器确认成墓碑（实现时补上，见决策日志）。

下一次状态检测时，被排除的文件节点 revision 仍高于基线：照旧判 ExternallyAdvanced，横幅只剩这些文件。
